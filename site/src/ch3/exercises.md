# 实现比较与练习

## 相同的任务，不同的切换路径

| 问题 | rCore 第三章 | uCore 第三章 |
| --- | --- | --- |
| 如何标识执行实体？ | 任务数组下标 | 进程表槽位与 PID |
| 用户状态保存在哪里？ | 各任务内核栈中的 `TrapContext` | 静态分配的 `trapframe` |
| 内核切换状态保存在哪里？ | 控制块中的 `TaskContext` | 控制块中的 `context`，以及 `idle.context` |
| 下一任务由谁选择？ | 当前任务调用的 `run_next_task` | 恢复后的 `scheduler` |
| 只剩一个任务时如何让出？ | 更新状态后直接返回 | 切回调度器，再恢复同一进程 |
| 退出后的状态是什么？ | `Exited` | `UNUSED` |
| 全部应用结束时怎样处理？ | 没有就绪任务时输出完成信息并关机 | `finished` 在最后一个应用结束时终止批次 |

两套切换汇编都保存 `ra`、`sp` 和 `s0`—`s11`。差异主要体现在调度循环所在的位置、状态表示和资源组织方式。

## 预测与验证

先根据源码回答，再在运行报告中查看相应事件和状态。

1. 三个任务依次就绪，任务 0 首先运行。任务 0 主动让出后，下一任务是谁？如果任务 1 已退出，选择如何变化？
2. 一次 `yield` 调用跨越了另一个程序的执行。为什么原程序的局部变量仍然可用？请分别指出用户变量与内核调用状态的保存位置。
3. 两个内核中，让出函数的调用次数是否等于切换汇编的调用次数？分别考虑首次启动、时钟抢占和只剩一个任务的情况。
4. 字符 A、B、C 的输出发生交错，能否仅凭输出顺序判断每次切换原因？还需要查看哪些事件？
5. 从时钟中断进入调度后，暂停程序再次运行时是否需要跳过一条指令？与系统调用路径中的 `sepc` 更新比较。

## 检查一个调度实现

在课程学生分支中实现接口时，可以按以下顺序检查：

- 首次运行前，用户入口、用户栈和初始内核上下文是否对应同一程序。
- 选择目标时，是否只接受就绪状态，并在有效槽位范围内扫描。
- 切换前，上下文存储是否有效，任务状态是否已经更新。
- 暂停后恢复，是否沿原来的内核调用继续。
- 退出后，是否还能被选中。

若程序只输出一轮便停滞，先区分没有就绪任务、恢复地址错误和状态未更新。分别查看任务表、切换参数与寄存器，再回到对应的代码分支。

## 本章小结

任务状态决定调度资格，上下文保存继续执行的位置。异常入口先保存用户状态，调度过程再保存内核调用状态。恢复内核上下文后，处理函数继续执行，随后返回用户态。

本章的程序和栈使用静态内存区域。第四章将进一步分析页表，使各程序拥有独立地址空间，并由硬件检查访问权限。
